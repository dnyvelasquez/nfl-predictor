- `npm run build` / `ng build` — production build to `dist/nfl-predictor`
- `npm run watch` — incremental dev build (no server)
- `npm test` / `ng test` — run Karma/Jasmine unit tests (all specs)
  - To run a single spec file, use Karma's `--include` or temporarily scope with `fdescribe`/`fit` in the spec — there is no built-in single-file CLI filter configured in this project

- `ng generate component components/<name>` — scaffold a new standalone component following existing conventions

## Architecture

This is an Angular 20 app (standalone components) backed by [Neon](https://neon.com) — Postgres plus its Data API (PostgREST-compatible) and Neon Auth (managed Better Auth). The site is deployed as a fully static client-side SPA on GitHub Pages; there is no custom backend — every table access and auth call goes straight from the browser to Neon's Data API / Auth service.

The project migrated from Supabase to Neon on 2026-08-25, as a follow-up to the same migration on the sibling project `fifa-predictor` (same author, same original architecture). The schema was carried over 1:1 except one deliberate change: Supabase had a public (`anon`) `UPDATE` RLS policy on `equipos` (anyone could edit team stats without logging in) — this was dropped, so writes now always require authentication. See `schema.sql` at the repo root for the DDL (tables, RLS policies, grants) applied to the Neon project.

**Not actually SSR**, despite appearances: `@angular/ssr`, `express`, `app.routes.server.ts` (`RenderMode.Prerender` for `'**'`), and `provideClientHydration()` are all present, but there is no `main.server.ts` and `angular.json`'s build target has no `server`/`ssr`/`prerender` keys wired up. `src/main.ts` just calls plain `bootstrapApplication()`. The app builds and deploys as an ordinary client-rendered SPA: every push to `main` triggers `.github/workflows/deploy.yml`, which runs `ng build --configuration production`, copies `index.html` to `404.html` for SPA routing fallback, and publishes to GitHub Pages — no manual deploy step — the SSR scaffolding is inert.

### Neon access layer

As of 2026-09-22, data access is split across several per-domain services under `src/app/services/`, the same shape as the sibling project `fifa-predictor` (used only as a loose reference — this split isn't a 1:1 copy; see the dated sections below for what's different). This replaced the original single 925-line `Service` god-class in `src/app/services/data.ts` (deleted), which had grown to cover every domain in the app.

- `src/app/services/core/supabase-client.ts` — `SupabaseClientService`, a thin injectable wrapper (`.from()`, `.auth()`, `.getClient()`) around the raw `supabase` client singleton (`src/app/core/supabase.client.ts`, unchanged — still created via `@neondatabase/neon-js`'s `createClient()` with the `SupabaseAuthAdapter`, `allowAnonymous: true`, etc.). Every domain service below injects `SupabaseClientService` instead of importing the raw client directly. `auth-guard.ts` and `login.ts` still import the raw `supabase` client directly for a couple of specific calls (unchanged from before the split). `supabase.client.ts` also gives the Data API a custom `fetch` that makes sure signed-in users' queries carry their JWT — see "Gotcha — silent anonymous fallback".
- `src/app/services/core/etapas.ts` — dependency-free pure module (no Angular injection, no Neon calls): the `Etapa` type, `ETAPAS` labels, and the etapa-scoring formula (`registroEquipoEnEtapa`, `marcaEquipoEnEtapa`, `estadoEquipoEnEtapa`, `marcaEquipoPorEtapa`). Both `EquiposService` and `ParticipantesService` need this same win/tie/loss/points calculation, so it lives here as plain functions rather than being duplicated or forcing one service to depend on the other.
- `src/app/services/auth/auth.ts` — `AuthService`: session (`login`, `logout`, `getSession$`, `isAuthenticated$`, `getUserId$`), the signed-in user's access (`getPerfil$()` → `{ esSuperusuario, membresias }`, `esSuperusuario$()`, `esAdministrador$()`), and user management (`crearUsuario`, `agregarMiembro`, `setRolEnGrupo`, `quitarDeGrupo`, `setSuperusuario`, `listUsers`, `deleteUser`) — see "Roles, grupos y privacidad". The Better Auth Admin-plugin calls go through the native client — **not** `supabase.auth.admin`, which is `undefined` on the `SupabaseAuthAdapter` in `@neondatabase/neon-js@0.7.0-beta` — but `supabaseClient.auth().getBetterAuthInstance().admin.{createUser,setRole,removeUser}` (private `admin()` helper). Neon Auth enforces the Better Auth `admin` role server-side (a non-admin session gets a hard rejection).
- `src/app/services/grupos.ts` — `GruposService`: the `Grupo`/`GrupoDisponible` types, `formatearApuesta()`, group CRUD (`getGrupos`, `crearGrupo`, `actualizarApuesta`, `borrarGrupo`), and the shared "selected group" (`gruposDisponibles$()`, `contexto$()`, `recordarGrupo()`, persisted in `localStorage`).
- `src/app/services/core/mascotas.ts` — pure module that builds each team's mascot-image URL from its name (see "Mascotas derivadas del nombre").
- `src/app/services/equipos.ts` — `EquiposService`: the `Equipo`/`EquipoStanding`/`EquipoRanking` types and `getEquipos`/`getEquiposDe`/`getEquiposDeTodasEtapas`/`getEquiposDelGrupo` (one query for a whole group's assignments)/`getEquiposConPuntajePorEtapa`/`getStandingsTemporadaRegular` (Fixture)/`getRanking` (Ranking inicial). Injects `JuegosService` for the "juegos con resultado" it needs to compute per-etapa scores.
- `src/app/services/juegos.ts` — `JuegosService`: the `Juego`/`EstadoJuego` types and the whole juegos/semana domain (CRUD, week navigation, `getJuegosConResultado` — finished games only, the base of every score —, `getJuegosPostemporada` (Fixture bracket), `rondaTerminada(etapa)`/`temporadaRegularTerminada()`, `getAnioTemporada()`, the private `enrichJuegos` logo/participant-attachment helper; `getJuegosPorSemanaId(semId, grupoId?)` attaches that group's holders).
- `src/app/services/participantes.ts` — `ParticipantesService`: the `Participante`/`RegistroEquipoParticipante` interfaces, participant CRUD, `asignarNumerosAleatorios` (`.rpc('sortear_numeros')`), and `getParticipantesConPuntaje` (injects `EquiposService` + `JuegosService` for the same reason `EquiposService` does).
- `src/app/services/asignacion.ts` — `AsignacionService`: the `Asignacion` interface, manual `assignEquipo`/`resetAsignaciones`/`getAsignaciones` (all per etapa and group), and the `.rpc()` wrappers for the SQL auto-assignment functions (`autoAsignarTemporadaRegular`, `autoAsignarWildcard`, `autoAsignarEliminatoria(grupoId, 'divisional' | 'conferencia' | 'superbowl')`).

Each service queries the Neon tables it needs directly via `SupabaseClientService` rather than always going through a sibling service for data it could fetch itself (e.g. `JuegosService` queries `equipos`/`asignacion` directly for `enrichJuegos` instead of injecting `EquiposService`/`AsignacionService`) — cross-service injection is used only where real computed logic needs to be shared (scoring), not for raw table reads.

### RLS

`schema.sql` enables Postgres RLS on every table. Current shape (details in "Roles, grupos y privacidad"):

- **Public NFL data** — `equipos`, `juegos`, `semana`: `SELECT` open to `anonymous` and `authenticated`.
- **Group data** — `participantes`, `asignacion`, `grupos`: no `anonymous` policy (the `GRANT SELECT` is kept on purpose, so anonymous queries return zero rows instead of a permission error); `authenticated` sees only rows of groups they belong to (`rol_en_grupo(grupo_id) IS NOT NULL`), the superusuario sees all.
- **Writes** on all domain tables: `authenticated` only when `public.es_superusuario()`. Every other write (an administrador's auto-assignment or adding read-only members) goes through `SECURITY DEFINER` SQL functions that check the role themselves.
- `roles_usuario` / `miembros_grupo`: each user reads their own rows (administradores also see their groups' members); writes are superusuario-only.

Neon's Data API role names are `authenticated`/`anonymous` (not Supabase's `anon`). RLS alone isn't sufficient on Neon — each role also needs an explicit `GRANT` (see `schema.sql`); a policy with no matching grant is silently never evaluated. The ESPN sync scripts connect as the DB owner via `DATABASE_URL`, so RLS doesn't apply to them. `schema.sql` is a fresh-DB DDL followed by the dated migrations in the order they were applied (run top to bottom); a few additive `juegos`/`equipos` columns synced from ESPN are only described here, not in it.

### Domain model

The app runs an NFL season-long prediction pool with these entities (Postgres tables in Neon):

- **equipos** (`Equipo` interface) — all 32 NFL teams, grouped by `division`. Still has 7 legacy stat columns (`pg/pe/pp/pw/pd/pc/sb`) in the schema, but as of 2026-08-27 **nothing reads or writes them anymore** — they're dead weight kept only because dropping columns needs a manual migration nobody's requested. The public `equipos` page (`src/app/components/equipos/`) was updated the same day to stop displaying them: each team's row now shows a per-etapa breakdown (`EquiposService.getEquiposConPuntajePorEtapa()`) of the participant holding that team and the points it earned, one line per etapa the team is actually assigned in — same `registroEquipoEnEtapa()` calculation described below, just grouped by team instead of by participant. As of 2026-09-21 it also has `espn_id` (text, unique when non-null) mapping the row to its team ID in the ESPN API — see "Sincronización automática con ESPN" below. As of 2026-09-22 it also has `ciudad` (text), rendered before the team name on the public `equipos` page — see "Ciudad de los equipos y caché del Data API" below. It also has `ranking` (smallint, 1 = Super Bowl champion, 32 = worst regular-season team), which drives the regular-season auto-assignment and the public "Ranking inicial" page — see "Ranking global de equipos" below — and `posicion_division` / `seed_conferencia` from ESPN's standings (see "Fixture"). `logo` is the official NFL.com logo (used by Fixture and Ranking); the illustrated mascots are not stored, their URLs are derived from `nombre`.
- **participantes** — the people competing in the pool, each in one `grupo` (`grupo_id NOT NULL`). Still has a persistent `acumulado` column in the schema, but it is **no longer read anywhere** — `ParticipantesService.getParticipantesConPuntaje()` stopped adding it to `puntaje` on 2026-08-27 (see below). Its `numero` column (used as pick/draft order, rendered as `"{{ p.numero }} - {{ p.nombre }}"` in `asignacion.html`) is assigned by a random draw (since 2026-09-22) and can also be corrected by hand by the superusuario — see "Sorteo de números de participantes" below.
- **asignacion** — assignment of teams to participants per group (`grupo_id`) and per `etapa` (`'regular' | 'wildcard' | 'divisional' | 'conferencia' | 'superbowl'`, see `Etapa`/`ETAPAS` in `core/etapas.ts`), so each round has its own independent set: in the regular season one team per division (4 per participant with 8 participants), in Wild Card/divisional/conference final one per conference, in the Super Bowl a single team. Uniqueness: `UNIQUE (equipo_id, etapa, grupo_id, participante)`, plus a partial unique index making a team single-holder in `regular`/`wildcard`; from the divisional round on, a team can have several holders (rule 16). `participante` stores the participant's **name** (not an id). A team's holders are derived by joining `equipos` with `asignacion`, joined with " / " when shared.
- **juegos** — schedule (`local`/`visitante` team names, `fecha`, `hora`, `semana` FK), plus `etapa` (same `Etapa`/`ETAPAS` domain as `asignacion`, added 2026-08-26) and nullable `resultado_local`/`resultado_visitante` (also added 2026-08-26, set from "Ingresar Juego"). As of 2026-08-27 these results are the **source of truth for scoring** (see below), not just informational display — `resultado_local`/`resultado_visitante` also still render on the public `Juegos de la semana` page once both are non-null (NULL/NULL means not played/entered yet, distinct from a real 0-0 score). `juegos` exists so `JuegosService.getJuegosSemanaActual()`/`getJuegosPorSemanaId()` can render "what's playing this week," and `JuegosService.actualizarJuego()` lets an admin edit any field of an existing game (recomputing `semana` from `fecha` if the date moves to another week). As of 2026-09-09 "Ingresar Juego" also has delete buttons per row (`JuegosService.eliminarJuego()`) and a "Borrar todos los juegos" action that clears the whole table (`JuegosService.eliminarTodosLosJuegos()`, an unfiltered `DELETE` expressed as `.not('id', 'is', null)` since the Data API requires a `WHERE` clause). As of 2026-09-21 it also has `espn_event_id` (text, unique when non-null), `estado` (text, default `'programado'`; one of `programado | en_vivo | final | pospuesto`), `periodo` (text, nullable — see below), and `actualizado_en` (timestamptz, default `now()`) — see "Sincronización automática con ESPN" below; these are additive columns not yet reflected in `schema.sql`'s fresh-DB DDL (same "apply manually on an existing Neon DB, then `NOTIFY pgrst, 'reload schema';`" pattern as the `etapa` column).
- **grupos** — independent pools (`nombre`, `apuesta`, `moneda`); participantes, asignacion and miembros_grupo reference it.
- **miembros_grupo** — which Neon Auth users belong to which group, with a role per group (`administrador` | `lectura`).
- **roles_usuario** — only marks the global superusuario. See "Roles, grupos y privacidad" for both.
- **semana** — defines week date ranges (`inicio`/`fin`) for the schedule's week-by-week navigation.

### Scoring is computed from game results (2026-08-27)

There is no more manual score entry. The old "Puntajes" admin page/route and `Service.actualizarPuntaje()`/`resetPuntajes()`/`acumularPuntajesEnParticipantes()` were deleted outright (not deprecated in place) — they wrote to `equipos.pg/pe/pp/pw/pd/pc/sb` and rolled that into `participantes.acumulado`, both of which are now unused.

`ParticipantesService.getParticipantesConPuntaje()` (backs `tabla-puntajes` and the `participante-dialog` popup opened from `Home`) now computes each participant's score directly from `juegos`: it fetches every `juego` with a non-null result once (`JuegosService.getJuegosConResultado()`), plus each participant's picks across **every** etapa (`EquiposService.getEquiposDeTodasEtapas()`, already etapa-aware from the 2026-08-26 work). For each `(equipo, etapa)` pick, the pure `registroEquipoEnEtapa()` function (`core/etapas.ts`, shared with `EquiposService` — see "Neon access layer" above) scans that etapa's finished games for one where `equipo.nombre` matches `juego.local` or `juego.visitante` (matched by **name**, since `juegos` stores team names, not ids) and tallies wins/ties/losses by comparing scores. **Only finished games count** (since 2026-10-04): `getJuegosConResultado()` excludes `estado IN ('en_vivo', 'pospuesto')` at the query, because the ESPN sync writes partial scores while a game is live — before this, standings moved with every live score; the SQL `puntajes_grupo()` applies the same filter. Losses count toward the visible record but contribute 0 points; a win scores that etapa's full value, a tie scores half — the same weights the old formula used (`regular`=10, `wildcard`=20, `divisional`=30, `conferencia`=40, `superbowl`=50), now applied **per etapa's own assignment** instead of always through the regular-season one. This closes the gap flagged in the 2026-08-26 asignación-por-etapa work (see below) — playoff picks now actually score.

**Bono de descanso de la primera semilla (2026-10-03).** The #1 seed of each conference doesn't play the Wild Card round, so whoever holds that team in the `wildcard` assignment gets the 20 points a Wild Card win would give (reglamento point 19). `registroEquipoEnEtapa(nombre, etapa, juegos, seedConferencia?)` adds them when `etapa === 'wildcard' && seedConferencia === 1` and returns `descanso: true`; the record label becomes "Descansó (1ª semilla)" (`marcaEquipoEnEtapa(..., descanso)`). The seed comes from `equipos.seed_conferencia` (ESPN `playoffSeed`, written by `syncStandings()`), which keeps moving during the season, so the bonus is **explicitly gated on the regular season being over** (the user asked for this so points never show up early): `JuegosService.temporadaRegularTerminada()` is true once there are regular-season games and none is `programado` or `en_vivo` (postponed games don't block; a rescheduled one goes back to `programado` on sync), and both scoring paths pass the seed only when it's true (`regularTerminada ? seed : null`). Without that gate a Wild Card assignment filled in early would have scored the bonus with a provisional seed. Both scoring paths pass the seed (`getEquiposDeTodasEtapas()` and `getEquiposConPuntajePorEtapa()` now select `seed_conferencia`). Verified with six cases (seed-1 bye = 20, seed-5 win = 20, loss = 0, seed-1 in regular/divisional = no bonus, unknown seed = no bonus).

**Reglamento rewritten (2026-10-03)** with the user: grouped into sections (Sorteo / Asignación en temporada regular / en playoffs / Puntos / Apuesta y premios) with continuous numbering via `<ol start>`, 26 rules. Decisions recorded there: the #1-seed bye bonus above; ties only exist in the regular season (5 points); a tie for first splits the whole pot and there's **no** second-place prize; teams left over when they don't fill a complete round are left unassigned (rule 7, matching the auto-assignment algorithm). The rules stay hardcoded in the HTML — only the bet (rule 22) comes from the DB, per group — until some group actually needs different rules.

`EquiposService.getEquiposConPuntajePorEtapa()` (backs the `equipos` page) reuses the same `registroEquipoEnEtapa()` helper from the opposite direction — per team instead of per participant — returning each team with a `porEtapa: RegistroEquipoPorEtapa[]` (etapa, label, participant, points), skipping etapas the team has no assignment in.

`Participante.equiposPorEtapa` (`{ etapa, label, equipos: RegistroEquipoParticipante[] }[]`, empty groups skipped) carries the computed `{ equipo, wins, ties, losses, puntos }` per pick straight from this calculation — `tabla-puntajes.html` and `participante-dialog.html` render it identically (both show a `wins-losses-ties` record plus `puntos` per team, grouped under an etapa heading); keep them in sync if this shape changes again, since they're two independent templates over the same data, not a shared component.

### Asignación por etapa (playoffs)

Added 2026-08-26. The `asignacion` component (`src/app/components/asignacion/`) renders one assignment grid (8 divisions × participantes, unchanged from before) per `Etapa`, switched via a `MatTabsModule` tab strip (first use of Material tabs in this codebase) — `etapaActiva` is a signal driving which etapa's rows are fetched; participantes/equipos master data loads once, only the `asignacion` rows are refetched on tab change. `AsignacionService.assignEquipo()`, `getAsignaciones()`, `resetAsignaciones()` all now take an `etapa` parameter (default `'regular'`), and the delete-before-insert in `assignEquipo()` is scoped by `etapa` too, so editing a cell in one stage cannot clear a participant's pick in another stage. **Reveal animation (2026-10-04).** After any "Auto-asignar" succeeds, the grid starts empty (`valorCelda()` hides teams not yet in `revelados` while `animando()`) and `revelarAsignacion()` reveals one team at a time in the order the rules hand them out — regular season by `equipos.ranking` (shows "Ranking #n"), playoffs AFC then NFC by `seed_conferencia` — showing the mascot, city and name in the center, then its holder(s), then a chip (created in code, styled via `:host ::ng-deep .ficha-vuelo`) flies to each holder's cell (`id="celda-{division index}-{participante id}"`), which flashes. ~3 s per team; "Saltar animación" ends it, `prefers-reduced-motion` skips it, and a `try/catch` always closes the overlay (the assignment is already saved). For the order/labels, `EquiposService.getEquipos()` now also selects `ranking` and `seed_conferencia`. Same visual language as the participants' number draw.

### Sincronización automática con ESPN (2026-09-21)

`scripts/sync-nfl.mjs` is a standalone Node script (not part of the Angular app/build — connects to Neon directly with `pg`, not through the Data API) that pulls schedule/results from ESPN's public, unofficial, key-less endpoint (`https://site.api.espn.com/apis/site/v2/sports/football/nfl/...`) and upserts them into `equipos`/`juegos`. It has two modes, chosen with the `MODE` env var:

- **`MODE=full`** (default) — matches every `equipos` row to its ESPN team by mascot name (`team.name` in ESPN's API, e.g. "Vikings", equals `equipos.nombre`) and sets `equipos.espn_id`, then walks all 22 weeks: regular season weeks 1–18 (ESPN `seasontype=2`) and postseason (`seasontype=3`, ESPN week mapped to `etapa`/`semana` via `POSTSEASON_WEEK_MAP`: 1→wildcard/19, 2→divisional/20, 3→conferencia/21, 5→superbowl/22 — ESPN's week 4 is the Pro Bowl and is skipped). Meant to run about once a week to pick up schedule changes, postponements, and newly-defined playoff brackets.
- **`MODE=quick`** — skips the `espn_id` refresh and the full 22-week walk. It first queries our own `juegos` table (`findWeeksNearToday()`) for which `(semana, etapa)` pairs have a game with `fecha` between "yesterday" and "the day after tomorrow" in Bogotá time; if none are found it exits immediately without calling ESPN at all. If it finds one or two, it syncs only those weeks via `toEspnWeekParams()`/`ETAPA_TO_ESPN_WEEK` (the inverse of `POSTSEASON_WEEK_MAP`). Meant to run very frequently (every 5 minutes, every day) — this is what actually catches Thursday games, occasional Saturday games, early international Sunday games, and Monday Night Football, without hardcoding day/time windows and without wasting ESPN calls or CI minutes on days with nothing to sync.

For each ESPN event returned by a synced week, `upsertGame()` writes to `juegos` in this priority: update the row with a matching `espn_event_id` if one exists → else link an existing manually-entered row (no `espn_event_id` yet) matching on `semana`+`etapa`+`local`+`visitante` → else insert a new row (id = current `MAX(id)+1`, tracked in-process across the run). This means games entered by hand through "Ingresar Juego" before the first sync get adopted rather than duplicated, as long as team names/week/etapa match exactly. Dates are converted from ESPN's UTC kickoff time to Bogotá time (UTC-5, fixed offset, no DST) into the same `fecha` (`YYYY/MM/DD`) / `hora` (`HH:MM` 24h) string format the rest of the app already uses; ESPN's game status is mapped to `juegos.estado` (`programado | en_vivo | final | pospuesto`) and `actualizado_en = now()` is stamped on every write, while `resultado_local`/`resultado_visitante` stay `NULL` while `estado = 'programado'`.

**`juegos.periodo` (2026-09-22).** Free-text label of the live game phase — `'1er cuarto' | '2do cuarto' | '3er cuarto' | '4to cuarto' | 'Medio tiempo' | 'Tiempo extra'`, or `NULL` when `estado !== 'en_vivo'`. Computed by `mapPeriodo()` in `sync-nfl.mjs` from the *same* ESPN `competition.status` object `mapEstado()` already reads (`status.type.name.includes('HALFTIME')` → "Medio tiempo"; else `status.period` → quarter 1-4 via a lookup table, `>= 5` → "Tiempo extra") — no extra ESPN request and no extra GitHub Actions time, since it rides on the poll the `quick`-mode loop was already making. The frontend (`juegos.html`) renders it as-is directly under the "En vivo" badge; it does no translation/mapping of its own, so if ESPN's period numbering or halftime signaling ever changes, fix it in `mapPeriodo()`, not in the component.

Run manually with Node ≥18 (uses native `fetch`) and the `pg` dependency (already in `package.json`); on Windows, set env vars PowerShell-style:

```powershell
$env:DATABASE_URL="postgres://..."; $env:SEASON_YEAR="2026"; $env:MODE="full"; node scripts/sync-nfl.mjs
```

`DATABASE_URL` is the Neon connection string (required); `SEASON_YEAR` defaults to `2026`, `MODE` defaults to `full` if omitted.

`.github/workflows/sync-nfl.yml` runs on this repo's unlimited public-repo Actions minutes, with two `schedule` triggers: `*/5 * * * *` (every 5 minutes, every day, all day — the shortest interval GitHub cron allows) runs in `MODE=quick`; `0 6 * * 2` (Tuesday 06:00 UTC = 01:00 Bogotá, after Monday Night Football has ended) runs in `MODE=full`. A "Determinar modo" step picks `MODE` from which cron fired the run (`full` only on the `0 6 * * 2` schedule, `quick` on every other scheduled tick) or from the chosen input when triggered manually — `workflow_dispatch` exposes a `mode` dropdown (`quick`/`full`, defaulting to `quick`) for on-demand runs from the Actions tab. It reads the Neon connection string from the repo secret `DATABASE_URL` (Settings → Secrets and variables → Actions) — never hardcoded — and pins `SEASON_YEAR` to `"2026"` in the workflow itself (update it there for the next season).

**GitHub does not actually honor `*/5 * * * *` (2026-09-22).** Confirmed in production: between the workflow's first two runs, GitHub fired the schedule at 2026-09-21T21:07Z and then not again until 2026-09-22T00:06Z — a ~3 hour gap for a "every 5 minutes" cron, during which a live game (Rams @ Giants) sat showing `estado='programado'` on the public site because nothing re-synced it. This isn't a bug in this repo's YAML; GitHub's scheduler is documented to delay/skip scheduled runs under load and gives no guarantee at sub-hourly granularity, and public/low-Actions-usage repos seem to get throttled hardest.

First fix attempt (superseded, see next paragraph): made the `quick`-mode step loop internally (`while`/`sleep 240` in bash) for up to 55 minutes per job. That only helped *while a triggered job was still running* — once its 55 minutes ran out, staleness came right back if the cron didn't fire again (observed again in production: a manually-triggered run finished its loop, and the live Rams @ Giants score sat stale at "4to cuarto" for 36+ minutes with nothing re-syncing until triggered manually a second time).

**Current fix: self-chaining via the GitHub API, not cron at all.** `sync-nfl.mjs`'s `runQuick()` writes `reencadenar=true|false` to `$GITHUB_OUTPUT` (`writeGithubOutput()`, a no-op outside Actions where that env var doesn't exist) based on the exact same `findWeeksNearToday()` check that already decides whether to call ESPN — `true` when some `(semana, etapa)` has a game within the -1/+2 day window, `false` otherwise. The workflow's "Reencadenar si todavía hay un juego cerca de hoy" step reads that output (`steps.sync.outputs.reencadenar`) and, if `true`, sleeps 240s then `curl`s a `POST /repos/{repo}/actions/workflows/sync-nfl.yml/dispatches` (needs `permissions: { contents: read, actions: write }` on the job — the default `GITHUB_TOKEN` can't dispatch workflow runs without that explicit grant) to trigger a fresh `mode=quick` run of itself, passing an incrementing `intento` input as a safety counter (capped at 200 ≈ 16-17h of continuous chaining, to stop a logic bug from chaining forever — no real game window gets anywhere close to that). The chain is entirely self-sustaining once started (by cron *or* a manual `workflow_dispatch`) and needs no further cron cooperation — it keeps itself alive exactly as long as `findWeeksNearToday()` keeps finding something nearby, and stops on its own once nothing is. `concurrency: { group: sync-nfl, cancel-in-progress: false }` still queues rather than overlaps if the flaky cron does happen to fire while a chain is active. `timeout-minutes: 10` on the job is enough for checkout+install+sync+the 4-minute sleep+dispatch; it does **not** need the old 60+ minute budget since the job no longer stays alive for the whole polling window itself. If you touch this workflow, keep both halves in sync: `reencadenar`'s logic in the script and the dispatch step's use of it.

**"En vivo" en `Juegos de la semana` (2026-09-21).** `JuegosService.getJuegosPorSemanaId()`/`getJuegosSemanaActual()` already select `juegos.*`, so `estado` flows through without any service change; it was added to the `Juego` interface as `estado?: EstadoJuego` (`EstadoJuego = 'programado' | 'en_vivo' | 'final' | 'pospuesto'`, `src/app/services/juegos.ts`). The `juegos` component (`src/app/components/juegos/`) uses it in two ways:

- **Display priority**: `juegos.html`'s per-game "scheduled" cell used to show "Final" whenever `resultado_local`/`resultado_visitante` were non-null. That broke once the ESPN sync started writing partial scores while a game is still in progress (`estado='en_vivo'`, resultado already set) — a live game would render as "Final". The cell now branches on `estado === 'en_vivo'` first: if true, it shows *only* the pulsing "En vivo" badge plus `j.periodo` underneath when present (no `hora`/clock icon — deliberately dropped so nothing implies a kickoff time for a game already in progress); otherwise it falls back to the original `resultado_local !== null && resultado_visitante !== null` check → "Final", else the scheduled `hora`. This keeps old manually-entered finals (no `estado`, defaulted to `'programado'` by the schema) working unchanged.
- **Auto-refresh**: `Juegos` (`juegos.ts`) polls `JuegosService.getJuegosPorSemanaId()` every 60s (`REFRESH_INTERVAL_MS`) via `setTimeout`, but only while `hayJuegosEnVivo()` is true for the currently displayed week — `scheduleAutoRefresh()`/`refreshGamesQuietly()` re-arm each other after every fetch and stop rearming once no game in the week is `en_vivo`, so weeks with nothing live never poll. The refresh is "quiet": it skips the `loading` flag/spinner (`refreshGamesQuietly()` is a separate path from the initial `loadGames()`), just replacing `juegosAgrupados` and calling `cdr.detectChanges()` (the component is `OnPush`). The pending timeout is cleared on week navigation (`prevWeek()`/`nextWeek()`) and `ngOnDestroy()` so a stale refresh can't land on the wrong week or a destroyed component. Since the GitHub Action's `quick` sync only runs every 5 minutes, this client-side polling surfaces a new score within at most ~1 extra minute of whenever the next sync lands, not in real time.

### Sorteo de números de participantes (2026-09-22)

The manual "Número" input on the `participantes` component (both the create form and the inline edit row) was removed — `participante.numero` is no longer something an admin types in directly. It's now assigned in one shot for every participant via a "Sortear números" button (`Participantes.sortearNumeros()`, `src/app/components/participantes/participantes.ts`, behind a `confirm()` since it overwrites whatever numbers were there), which calls `ParticipantesService.asignarNumerosAleatorios(grupoId)` (`src/app/services/participantes.ts`): it fetches the selected group's participants, generates a Fisher–Yates shuffle of `1..N` (N = participant count in that group), and updates every row's `numero` in one `forkJoin` of per-row `UPDATE`s. `ParticipantesService.createParticipante(nombre)` no longer takes a `numero` argument either — since the column is `NOT NULL` with no DB default, it auto-assigns `MAX(numero) + 1` as a throwaway placeholder on insert (a `SELECT` before the `INSERT`); that placeholder is only there to satisfy the constraint and is expected to be overwritten the next time someone clicks "Sortear números", not a real draft-order assignment. There's no uniqueness constraint on `numero` in the schema, so nothing stops two participants from temporarily sharing a placeholder before the next draw.

**Manual edit is back (2026-10-04).** The inline edit row (superusuario only, like Editar/Eliminar) now has a "Número" field next to the name; `saveEdit()` sends `{ nombre, numero }` to `updateParticipante()` and re-sorts the list. Repeated numbers are allowed on purpose (the user needs them to reassign, e.g. swapping two participants one row at a time); the success message just warns who else has that number. There's no DB uniqueness on `numero` either. "Sortear números" is unchanged.

**Who can do what (2026-10-04).** Manual number edits stay superusuario-only (the Editar button). The draw is open to the selected group's **administradores** too (`Participantes.puedeSortear`, role from `GrupoDisponible.rol`): since they can't write `participantes` directly, `asignarNumerosAleatorios()` now calls the `SECURITY DEFINER` SQL function `sortear_numeros(p_grupo)` (role check, then a `row_number() OVER (ORDER BY random())` shuffle of 1..N in one `UPDATE`, returns the rows; DDL at the end of `schema.sql`) instead of the old client-side Fisher–Yates + per-row `UPDATE`s. The draw plays a CSS reveal animation (`revelarSorteo()`: highest number first, number then name in the center, both fly to their row; "Saltar animación" skips it, `prefers-reduced-motion` skips it, and a `try/catch` always closes the overlay since the numbers are already saved).

`equipos` gained a `ciudad` column (text, e.g. `"Buffalo"` for the Bills) — added directly in Neon and populated for all 32 teams, not yet reflected in `schema.sql`'s fresh-DB DDL (same "additive column, apply manually" situation as `espn_id`/`logo_2` before it). `Equipo.ciudad` was added to the interface (`src/app/services/equipos.ts`), and `equipos.html` now renders `{{ e.ciudad }} {{ e.nombre }}` (e.g. "Buffalo Bills") instead of just the team name.

### Ranking global de equipos (2026-09-22)

Reglamento rule #2 assigns teams to participants following "el ranking global de la temporada anterior" (`equipos.ranking`, smallint: 1 = Super Bowl champion, 32 = the team with the worst regular-season record — the inverse of NFL Draft order). It's read by the regular-season auto-assignment (see below) and, since 2026-10-03, shown on the public **Ranking inicial** page (`/ranking`, `components/ranking/`, under the header's "Equipos" submenu): `EquiposService.getRanking()` (official `logo`, `ciudad`, `division`, `ranking`) grouped into the same tiers `sync-ranking.mjs` builds — 1 champion, 2 runner-up, 3-4 conference-final losers, 5-8 divisional losers, 9-14 Wild Card losers, 15-32 non-playoff (hardcoded `NIVELES`, assumes the current 14-team playoff format). The season label ("2025-2026") isn't hardcoded: it's the year before the one the first `semana` starts in (`JuegosService.getAnioTemporada()`).

**Why not just load ESPN's actual Draft order:** ESPN's core API does expose the completed Draft pick-by-pick (`sports.core.api.espn.com/v2/sports/football/leagues/nfl/seasons/{year}/draft/rounds`), and its team references match `equipos.espn_id` directly — but round 1 reflects the *actual, post-trade* picks: verified live for the 2026 draft, only 24 of 32 teams appear in round 1 (some picked 2-3 times after trading up, 8 teams have zero picks because they traded their slot away). That data can't be turned into a clean 1-32 ranking per team. It's also not available ahead of time: `seasons/{year}/draft` for the season still being played returns `"picks": []` until ESPN populates the actual draft (~April) — confirmed live for the 2027 draft while the 2026 season was in progress, so relying on it wouldn't let this run automatically right when the Super Bowl ends anyway.

**What we do instead:** `scripts/sync-ranking.mjs` computes the ranking itself from ESPN's plain scoreboard results (`site.api.espn.com/.../scoreboard?dates={year}&seasontype={2|3}&week={n}` — historical seasons work with `dates`, not `year`, which silently returns the *current* season instead) using the NFL's own published draft-order rule, inverted:

1. The 18 non-playoff teams, worst-to-best regular-season record.
2. The 6 Wild Card losers, worst-to-best regular-season record.
3. The 4 Divisional Round losers, worst-to-best.
4. The 2 Conference Championship losers, worst-to-best.
5. The Super Bowl loser.
6. The Super Bowl winner.

Each team's furthest playoff round is found by walking `wildcard → divisional → conferencia → superbowl` in order and always overwriting a per-team map, so the last write is necessarily their furthest appearance. Ties within a group on win% are broken by strength of schedule (average opponent win%, weaker schedule sorts as "worse" — the same direction the NFL uses for actual draft-order tiebreaks), computed from the same regular-season game log already fetched, no extra requests. The resulting worst-to-best order (draft position 1-32) is inverted (`ranking = 33 - posición`) and written with a single `UPDATE ... FROM (VALUES ...)` matched by team name.

**Timing:** SEASON_YEAR here means the same thing it means in `sync-nfl.mjs` — the season being ranked, not the calendar year of the draft it feeds (e.g. `SEASON_YEAR=2025` was used for the one-off initial load, to rank the 2025-2026 season that produced the actual April-2026 draft). Since the computation only depends on our own historical scoreboard data — available the moment the Super Bowl ends — `.github/workflows/sync-ranking.yml` runs it daily from Feb 1-20 (`0 12 1-20 2 *`, comfortably bracketing the Super Bowl's usual date) plus `workflow_dispatch` for manual runs; the script itself checks this database's own `juegos` row with `etapa='superbowl'` first and exits without calling ESPN at all if that game has no result yet, so the early daily runs in the window cost nothing. `SEASON_YEAR` is pinned in the workflow (same pattern as `sync-nfl.yml`) and needs updating there each year.

The initial load (2026 draft / 2025-2026 season) was run once by hand via direct SQL against Neon rather than through the script with a materialized `DATABASE_URL`, since Claude Code's auto-mode classifier blocks putting a raw DB credential into a shell command; the ranking math was run client-side in a browser tab against the same ESPN endpoints instead, and the result written with `UPDATE equipos ... FROM (VALUES ...)`. A human running `scripts/sync-ranking.mjs` locally or in CI (where the secret comes from `secrets.DATABASE_URL`, not a typed command) doesn't hit this restriction.

### Auto-asignación de temporada regular por ranking (2026-09-22)

**Moved to SQL on 2026-10-02:** the algorithm now lives in Neon as `calcular_auto_asignacion_regular()` (computes only) + `auto_asignar_temporada_regular()` (role check, then delete-then-insert of `etapa='regular'` in one transaction), both `SECURITY DEFINER` (DDL in `schema.sql`); `AsignacionService.autoAsignarTemporadaRegular()` is now just an `.rpc()` call. It was moved so the `administrador` role can run it without having direct write access to `asignacion`. The SQL port was verified against the JS version by diffing its output with the existing `regular` rows (32/32 identical) before the JS was removed. If you change the rules, change the SQL function — the description below still applies, just read "the code" as the plpgsql.

`AsignacionService.autoAsignarTemporadaRegular()` implements reglamento rules #2, #5, #7 and #8 to fully automate the "Temporada Regular" grid, exposed as the "Auto-asignar" button on the `asignacion` component's Temporada Regular tab (the playoff tabs have their own score-based algorithms, see the next sections). It reads `participantes`/`equipos` fresh on every call — deliberately not assuming any ordering between when `equipos.ranking` gets loaded (see above, right after the Super Bowl) and when the next season's participants/`numero` draw exist, since those two things can happen in either order.

**Algorithm** (built and verified incrementally across several conversation turns, comparing each round's output against a manually-built assignment before trusting the next one): equipos are walked once in ranking order (1 = best) and hard the whole way through, distributed across the participants in fixed-size "rounds" of `N` (`N` = participant count) — round 1 in ascending `numero` order, round 2 descending, alternating every round (rule #5), for as many complete rounds as `Math.floor(equipos.length / N)` allows (currently 4, with 8 participants and 32 teams; genuinely N-agnostic — with e.g. 7 participants it does 4 rounds of 7 = 28 teams, leaving the 4 worst-ranked teams unassigned rather than giving one participant an uneven 5th team). Within a round, each team is offered to the front of that round's participant queue; a participant is skipped (team offered to the next-in-queue instead, immediately, exactly per the reglamento's wording) when they already hold another team from that division (#7) or already hold two teams from that team's conference (#8, "tercer equipo de una conferencia") — the skipped participant is *not* removed from the queue, so they're first in line again for the very next team, which is what rule #7's "el siguiente equipo le será asignado al participante que fue saltado" describes. `autoAsignarTemporadaRegular()` fully replaces `asignacion` for `etapa='regular'` (delete-then-insert) rather than patching individual cells.

One discrepancy surfaced during verification: a hand-built assignment had `Titans`↔`Tomás` and `Raiders`↔`Juan R` swapped relative to the algorithm's `Titans`↔`Juan R`/`Raiders`↔`Tomás`. Traced by hand pick-by-pick and confirmed the algorithm is correct — at that point in the queue (descending `numero`: ..., Juan R(4), ..., Tomás(2), ...) Juan R was skipped once earlier in the round and, per rule #7, got first crack at the very next team (Titans) before the queue ever reached Tomás; the manual assignment hadn't re-offered the skipped participant the next pick immediately. Confirmed as a one-off manual error, not an algorithm bug — worth remembering if a future manual-vs-algorithm mismatch shows up again, since "who was skipped most recently gets served first" is easy to get wrong by hand but is exactly what the code enforces.

### Auto-asignación de la ronda de comodines (2026-10-04)

Same shape as the regular-season one: `calcular_auto_asignacion_wildcard(p_grupo)` (computes only, returns each pick with a `motivo`) + `auto_asignar_wildcard(p_grupo)` (role check — superusuario or that group's administrador — then delete-then-insert of `etapa='wildcard'` for the group), both `SECURITY DEFINER`, DDL in `schema.sql`. `AsignacionService.autoAsignarWildcard()` is the `.rpc()`; the `asignacion` page shows "Auto-asignar" on both the Temporada Regular and Wild Card tabs (`etapasAutomaticas`), and on Wild Card the confirm warns when the regular season isn't over yet (it then uses ESPN's provisional seeds — useful for testing, re-run it when the season closes). It's not blocked mid-season on purpose.

Reglamento rules 11-16 and 19 left several things open; the user decided (2026-10-04):
1. **#1 seeds:** whoever holds a conference's #1 seed (`equipos.seed_conferencia = 1`) in the regular-season assignment goes into the Wild Card round with **only** that team — it has a bye that counts as a win (the +20 bonus) — and gives up their other teams. That's what makes the numbers work without sharing: 8 participants, 2 of them on a bye, 6 left for the 6 teams that actually play in each conference (seeds 2-7). The user explicitly rejected sharing teams for this reason.
2. **Keeping:** everyone else keeps their still-alive (seed 2-7) regular-season teams, one per conference; with two in the same conference they keep the one with the **better record**, ceding the other.
3. **"Mejor récord"** = regular-season win % (tie = half a win), **tie-broken by ESPN seed** — not the seed alone, so a 3-0 wild card ranks above a 2-1 division winner.
4. **Filling:** participants who still lack a conference are served in ascending score order (`puntajes_grupo()`, the same formula as the frontend, verified equal to the home page's numbers), ties by `numero` ascending (confirmed by the user), each taking the best-record free team in the missing conference.

Verified on 2026-10-04 with provisional week-4 seeds against the Grupo principal assignment: 14 picks, every playoff team exactly once, Tomás/Nicolás alone with Vikings/Chiefs, Federico keeps Lions over Seahawks and Juan M keeps Ravens over Broncos (both pairs 2-1, decided by seed), lowest-score Juan R gets Raiders (seed 5, 3-0) over Jaguars (seed 4, 2-1). Edge case not handled specially: if the same participant held **both** #1 seeds, 7 participants would compete for 6 teams per conference and the last one in order would get nothing in that conference (no sharing). The later rounds were automated the same day (next section). The reglamento text was updated the same day without renumbering: rule 11 states the #1-seed exception, rule 12 defines "mejor récord" (win %, tie-break by official seed) and the score tie-break (lower `numero` first), rule 14 says the better record is kept.

### Auto-asignación de las rondas eliminatorias: divisional, final de conferencia y Super Bowl (2026-10-04)

`calcular_auto_asignacion_divisional(p_grupo)` / `auto_asignar_divisional(p_grupo)`, same pattern and permissions as Wild Card; button on the Divisional tab (`etapasAutomaticas` now includes `'divisional'`). Alive teams = the two #1 seeds plus the winners of Wild Card games that have a result (computed from `juegos`, not from the divisional schedule — ESPN pre-creates every playoff game as `TBD` vs `TBD` with no result, and those are ignored everywhere). With 4 alive teams per conference and 8 participants, **sharing is unavoidable** (rule 16): each participant keeps their still-alive Wild Card teams, then in ascending score order (`puntajes_grupo()`, ties by `numero`) fills the missing conference with the team that has the **fewest participants so far**, then best record (win %, tie-break seed) — the user chose this "no team gets a third holder while another has one" balance on 2026-10-04, so with 8 participants every alive team ends up with exactly two. Rule 16 in the reglamento was clarified accordingly (no renumbering).

To allow sharing, `asignacion`'s uniqueness changed: `UNIQUE (equipo_id, etapa, grupo_id, participante)` everywhere, plus a partial unique index `asignacion_equipo_unico_sin_compartir ON (equipo_id, etapa, grupo_id) WHERE etapa IN ('regular', 'wildcard')` so the first two stages stay one-holder-per-team. Manual assignment through the grid (`assignEquipo()`, which swallows `23505`) therefore can now give a divisional+ team to several participants. The frontend already renders multiple holders joined with " / ".

The confirm dialog on playoff tabs checks whether the **previous** round is over (`JuegosService.rondaTerminada(etapa)` — generalizes `temporadaRegularTerminada()`; ESPN's `TBD` placeholders count as unfinished). Verified on 2026-10-04 on a throwaway Neon branch (`prueba-divisional`): applied the Wild Card auto-assignment, inserted six simulated Wild Card results (two upsets), and the divisional output matched a hand calculation — 16 picks, every alive team with exactly two holders. Caveat of that test: the regular season wasn't over on the branch, so the #1-seed bonus didn't count toward the ordering scores. **Generalized the same day for the conference final:** the logic now lives in `calcular_auto_asignacion_eliminatoria(p_grupo, p_etapa)` / `auto_asignar_eliminatoria(p_grupo, p_etapa)` for `'divisional'` (previous round `wildcard`, plus the #1 seeds) and `'conferencia'` (previous round `divisional`); `calcular_auto_asignacion_divisional`/`auto_asignar_divisional` were kept as thin wrappers so the already-deployed frontend kept working. Verified on another throwaway branch (`prueba-conferencia`): simulated Wild Card + divisional rounds (re-checking that divisional output was unchanged through the generic function), then the conference final matched a hand calculation — 16 picks, each of the 4 alive teams with exactly 4 holders. **Super Bowl (same day) — every playoff round is now automatic.** The user called rule 11's "one team per conference" wrong for the Super Bowl (everyone would hold both finalists, so the game couldn't change the standings): there each participant holds **one** team and participants are split **evenly** between the two finalists. `calcular_auto_asignacion_superbowl(p_grupo)` (`auto_asignar_eliminatoria` dispatches `'superbowl'` to it): (1) whoever holds one finalist in their conference-final assignment keeps it; holding both, they keep the better record; (2) if keepers leave one finalist over `ceil(N/2)`, the highest-score keepers on that side move to the other (user chose strict balance over "nobody loses a kept team"); (3) the rest, ascending score, go to the finalist with fewer holders, then better record. Because the finalists come from different conferences they can tie on record **and** seed (two #1 seeds is common), so the Super Bowl ordering adds regular-season **point differential** as a third tie-break — my default, stated in rule 12, not explicitly confirmed. With 8 participants balanced 4-per-team in the conference final, step 2 can never trigger on its own (each finalist has at most 4 keepers); it only matters after manual edits. Verified on a throwaway branch (`prueba-superbowl`): full simulated postseason, Chiefs vs Vikings both 3-0/#1 seed decided by +38 vs +30, 4/4 split matching a hand calculation; then a manual skew (6 Chiefs keepers) correctly moved the two 180-point participants to the Vikings. Reglamento rules 11 and 12 were rewritten accordingly (no renumbering); `etapasAutomaticas` and `RONDA_ANTERIOR` include `'superbowl'`.

**Order within a division comes from ESPN, not from our own tiebreaker logic** (decided 2026-09-25). The NFL's official division tiebreakers (head-to-head → division record → common games (min. 4) → conference record → strength of victory → strength of schedule → points rankings → net points → net touchdowns → coin toss, restarting at step 1 whenever a multi-team tie shrinks) were evaluated for local implementation and rejected: net touchdowns isn't derivable from `juegos` (final scores only), the multi-team restart procedure is fiddly, and name-matched `juegos` rows make it fragile. Instead `scripts/sync-nfl.mjs`'s `syncStandings()` reads ESPN's standings endpoint (`site.api.espn.com/apis/v2/sports/football/nfl/standings?season={SEASON_YEAR}&seasontype=2&level=3` — note `/apis/v2`, not `/apis/site/v2`; `season` *is* honored here) and writes each team's 1-4 position into `equipos.posicion_division` (smallint, nullable, `CHECK 1..4`; additive column, not in `schema.sql`), matched by `espn_id` in one `UPDATE ... FROM (VALUES ...)`. It uses the order of each division's `entries` array — **not** `playoffSeed`, which is the conference seed and follows wild-card tiebreak rules that can disagree with the in-division order. Runs at the end of `MODE=full` and at the end of every `MODE=quick` run that found games near today (one extra request per run); skips the write if ESPN returns anything other than 32 teams. Spot-checked on 2026-09-25 against our own `juegos`: Giants>Cowboys (head-to-head), Seahawks>49ers and Steelers>Browns (strength of victory) all correct. The fixture sorts by `posicion_division` when every team in the division has one, else falls back to win% (tie = half a win), no tiebreakers. The initial load was done by direct SQL (same Claude Code credential restriction described under "Ranking global de equipos").

**Styling (2026-10-03):** each conference is a dark `mat-card` (like the other pages' containers) with the shared purple-gradient header (`#667eea` → `#764ba2`, the same as Equipos/Ranking card headers) and the conference logo in a white circle; division cards stay white with their AFC-red/NFC-blue band. **Row colors = playoff qualification.** Each team row gets a left border driven only by `seed_conferencia` (`Fixture.claseFila()`): yellow = seed 1 (the conference's only Wild Card bye), blue = the other division champions (seeds 2-4), red = wild cards (seeds 5-7), none = out of the playoffs. `equipos.seed_conferencia` (smallint, nullable, `CHECK 1..16`, additive, not in `schema.sql`) is ESPN's `playoffSeed` stat, written by the same `syncStandings()` call as `posicion_division` — ESPN applies the official wild-card tiebreakers, which is why it's stored separately instead of derived from division order.

### Roles, grupos y privacidad (2026-10-02 → 2026-10-04)

Built over several iterations; this section describes the **current** state.

**Groups.** Each `grupo` is an independent pool with its own participants and its own assignment for every etapa (all pre-existing data was backfilled into **"Grupo principal"**). `grupos` also stores the bet: `apuesta numeric(12,0)` (nullable, `>= 0`) + `moneda` (default `'COP'`); "Grupo principal" = 50000, rendered as `"$50.000 COP"` by `formatearApuesta()` and shown in reglamento rule 22 for the selected group. Groups are created, edited (bet) and deleted (only when empty — FKs return `23503`, surfaced as a friendly message) by the superusuario on the "Usuarios" page.

**Roles.** `roles_usuario` only marks the global **superusuario** (`CHECK (rol = 'superusuario')`; `dny.velasquez@gmail.com`), who sees and edits everything in every group. Everyone else gets access through `miembros_grupo (user_id → neon_auth."user" ON DELETE CASCADE, grupo_id, rol 'administrador'|'lectura', PK (user_id, grupo_id))` — a user can belong to several groups with a **different role in each**. What each role can do:
- **superusuario**: manual assignment, participants (including editing their numbers by hand) and the number draw, entering/editing games, users, roles, groups and bets.
- **administrador** (of a group): read-only in the admin pages, plus "Auto-asignar" (any etapa), the participants' number draw ("Sortear números") for that group, and creating read-only users in it.
- **lectura**: no admin pages at all — the shared per-group account the user planned; signs in to see the group's standings, holders and bet.

SQL helpers (`SECURITY DEFINER`, reading `auth.user_id()`): `es_superusuario()`, `rol_en_grupo(p_grupo)` → `'superusuario' | 'administrador' | 'lectura' | NULL`. The auto-assignment functions and `agregar_miembro(p_email, p_grupo, p_rol)` check them before writing (`agregar_miembro`: superusuario any group/role, administrador only `'lectura'` in groups they administer; looks the user up by email; `ON CONFLICT DO NOTHING`, so it never changes an existing member's role). `usuarios_visibles()` returns one row per (user, group) — superusuario sees everyone, an administrador the members of their groups — and backs the "Usuarios" page.

**Better Auth's own role** is kept in sync only as far as the Admin plugin needs it: superusuario ↔ `'admin'`, everyone else ↔ `'user'` (`setSuperusuario()` calls `admin.setRole()` then writes `roles_usuario`). Neon Auth only lets Better Auth admins call the Admin plugin, so keep both in sync. Administradores are deliberately **not** Better Auth admins — that role would let them call every Admin-plugin endpoint directly, including impersonating the superusuario. So `AuthService.crearUsuario(email, password, grupoId, rol)` branches: the superusuario uses `admin.createUser()`; an administrador calls Neon Auth's public `POST {neonAuthUrl}/sign-up/email` with a raw `fetch(..., { credentials: 'omit' })` (the new user's session cookie is discarded, the administrador stays signed in). Either way an "already exists" error just means "add the membership", then `agregar_miembro()` runs. **This depends on email/password sign-up staying enabled in Neon Auth** (`allow_sign_up: true`); the flip side is that anyone can self-register and end up with no group (no group data visible, writes rejected).

**Privacy.** See "RLS": group data (`participantes`, `asignacion`, `grupos`) is readable only by the group's members and the superusuario; NFL data stays public. Verified by simulating anonymous / superusuario / a user with no groups.

**Gotcha — silent anonymous fallback (2026-10-04).** After group data went private, signed-in users intermittently saw "Tu usuario todavía no pertenece a ningún grupo" or a standings table where some participants had 0 points, different on every reload. Cause is in `@neondatabase/auth@0.5.0-beta`: for **every** Data API request, `neon-js` calls `getJWTToken()`, which calls Better Auth `getSession()` and, if that doesn't yield the session's JWT at that moment, **silently falls back to an anonymous token** (`sub`/`role` = `'anonymous'`) instead of failing. Concurrent `getSession()` calls share one in-flight request (`BETTER_AUTH_METHODS_IN_FLIGHT_REQUESTS.deduplicate`), so when it fails, every query waiting on it goes anonymous together. Anonymous requests get zero rows from the group tables (no error, thanks to the kept `GRANT`). Before privacy everything was public, so it was invisible.

Fix, in two rounds (the first — just re-asking the session when a request was anonymous — still failed intermittently, because it went through the same flaky path): `src/app/core/supabase.client.ts` gives the Data API a custom `fetch` (`dataApi.options.global.fetch`, called after `neon-js` sets `Authorization`). It (1) keeps the **user's JWT in memory** once seen (from any request that carried it, or from a lookup) until 30 s before its `exp`, and uses it whenever a request isn't carrying a user JWT; (2) otherwise looks it up once at a time (`supabase.auth.getSession()`, then Better Auth `token()` from the bundled `jwtClient` if the session token is the opaque one), **retrying up to 4 times** if a `localStorage` flag (`nfl-predictor.sesion`) says this browser had a session; (3) remembers "no session" for 30 s so anonymous visitors don't trigger a lookup per query. `AuthService.login()`/`logout()` call `olvidarSesionDataApi()` (logout also clears the flag) so a cached JWT can't outlive its user. Console messages: `[neon] La consulta iba sin token de usuario pese a haber sesión: se corrigió.` (warn) and `[neon] Había sesión … no se pudo obtener su token` (error) — the way to confirm what's happening in production, since this can't be reproduced from this environment (needs a signed-in browser). **Third round (2026-10-07):** it still happened once, with **no** console message. Silent path: when the `localStorage` flag was missing, the lookup made a single attempt and gave up quietly (plus the 30 s "no session" cache); and the failure branch itself cleared the flag, so one failure disabled the retries for every later load. Now (1) `AuthService.getSession$()` passes every session it sees to `notarSesionDataApi(session)`, which stores its JWT (or at least sets the flag) — the same session that makes the UI say "signed in" now authorizes the queries, and `getPerfil$()` always goes through it first; (2) a failed lookup no longer clears the flag (only logout does); (3) `GruposService.contexto$()` retries once after 800 ms when a signed-in user comes back with no groups, before the pages show "no perteneces a ningún grupo". **Fourth round (2026-10-08):** it happened again, still silent, so it's probably not an anonymous token at all. Two silent paths were closed: (a) a **user JWT that was expired or older** was accepted as-is (only "is it a user's?" was checked) — now only JWTs valid for 30+ more seconds count, the cache keeps whichever expires latest, and a `401` from the Data API triggers `refrescarTokenDataApi()` (fresh JWT straight from the server via Better Auth `token()`, bypassing the library's session cache) plus one retry of that request; (b) `getPerfil$()` turned query errors into an empty profile without a trace — now it logs `[perfil] No se pudo leer el perfil…`. `contexto$()` now retries up to twice (600 ms, then 1200 ms), forcing a fresh JWT before each try. Diagnostics: `[grupos] Sin grupos disponibles {superusuario, membresias, gruposVisibles}`, `[grupos] …aparecieron en el reintento N` and `[grupos] Con sesión pero sin grupos tras reintentar` with `diagnosticoDataApi()` (sub/role/expiry/status of the last request, never the token itself) — if it recurs, those lines say which query came back empty and with what token. Also: `AuthService.getPerfil$()` doesn't cache an empty profile, and `getParticipantesConPuntaje(grupoId)` now loads the whole group's assignments in **one** query (`EquiposService.getEquiposDelGrupo()`) instead of one per participant, which cuts the number of concurrent requests (and fixed a hang: `forkJoin([])` never emits, so a group with no participants used to spin forever).

**Frontend.** `AuthService.getPerfil$()` (cached per user, cleared on login/logout); `esSuperusuario$()`, `esAdministrador$()` (superusuario or administrador of ≥1 group). Every page that shows group data shares one "selected group": `GruposService.contexto$()` → `{ logueado, grupos, seleccionado }`, `gruposDisponibles$()` returns `GrupoDisponible` (group + the caller's role in it), and `recordarGrupo()` persists the choice in `localStorage` (`nfl-predictor.grupo`, try/catch). `SelectorGrupo` (`components/selector-grupo/`) renders a `mat-select` with several groups, or just the name with one. Per page: the home page, **Tabla de puntajes** and **Equipos en competición** need a session for group data (sign-in prompt with `?redirect=…` otherwise); **Juegos de la semana** stays public and shows each team's holder only with a session; **Reglamento** is public but rule 22 (bet) comes from the selected group. In admin pages, `asignacion`'s `puedeAutoAsignar` is a `computed` over the **selected** group's role, and manual edit controls are hidden unless superusuario (cosmetic — RLS is the real enforcement). "Nuevo usuario" lists only groups the caller can add to and locks the role to "Solo lectura" unless superusuario; if the email already has an account it just adds the membership. "Usuarios" (superusuario) has a superusuario checkbox, per-group role selects, remove/add memberships, and group management; the signed-in user can't change their own superusuario flag or delete themselves.

**Testing RLS/SQL functions from the Neon MCP:** `select set_config('request.jwt.claims', '{"sub":"<user uuid>","role":"authenticated"}', true)` in the same `run_sql_transaction` makes `auth.user_id()` return that user. To test policies, also `SET LOCAL ROLE authenticated` — but call one of the `SECURITY DEFINER` helpers once **before** `SET ROLE`: the first call made under `authenticated` came back as if there were no user. Right after a migration that replaced these functions, the first check also returned stale results once; re-run before concluding anything broke. Calling `auth.user_id()` directly under `authenticated` fails with "permission denied for schema auth", which is expected (the app only reaches it through definer functions). For algorithm tests that need data that doesn't exist yet (e.g. playoff results), create a throwaway Neon branch, simulate there, and delete it afterwards (deleting needs the user's OK).

### Routing & auth

Routes are defined in `src/app/app.routes.ts`. Admin/management routes (`admin`, `nuevo-usuario`, `borrar-usuario`, `ingresar-juego`, `participantes`, `asignacion`) are protected by `authGuard` plus `rolGuard('administrador')` (`borrar-usuario`: `rolGuard('superusuario')`) — read-only users can't open any of them; `login` is protected by `guestGuard` (redirects an authenticated user to `/admin`, or to `/` if they're read-only). Public routes (`''`, `tabla-puntajes`, `equipos`, `fixture`, `ranking`, `juegos`, `reglamento`) require no auth, although the pages showing group data ask for a session (see "Roles, grupos y privacidad"). `login`, every admin route (since 2026-10-03) and the less-visited public pages `equipos`, `fixture`, `ranking`, `reglamento` (since 2026-10-04) are **lazy-loaded** (`loadComponent`); only `''`, `tabla-puntajes` and `juegos` stay in the initial bundle (1.24 MB, under the 1.30 MB budget). The guards still run before a chunk is downloaded. The header recomputes an `acceso` signal on every navigation: anonymous users and admins see "Admin", read-only users see "Cerrar sesión" instead. Unlike `fifa-predictor`, user creation and user management are two separate routes (`nuevo-usuario`, and `borrar-usuario`, labelled "Usuarios" in the UI) rather than one combined page, and there is no FIFA-Annex-C-style manual bracket-seeding step: the playoff bracket shown in the Fixture is derived from ESPN's seeds and results (see "Postemporada").

### Component conventions

Components are standalone and import Angular Material modules directly per-component (no shared Material module). Most data-loading components use RxJS (`forkJoin`/`switchMap`) directly against the domain services' methods rather than `async` pipes throughout; newer ones (home, ranking, tabla-puntajes, asignacion) hold their state in signals. The only shared UI component is `SelectorGrupo`. The Material theme is **dark** (`custom-theme.scss`): text inside `mat-card` must use light colors, while the white inner cards (Equipos, Ranking, Fixture divisions, Tabla de puntajes) use dark text; card headers share the purple gradient `#667eea` → `#764ba2`.
