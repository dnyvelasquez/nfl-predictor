# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Commands

- `npm start` / `ng serve` — dev server at `http://localhost:4200`
- `npm run build` / `ng build` — production build to `dist/nfl-predictor`
- `npm run watch` — incremental dev build (no server)
- `npm test` / `ng test` — run Karma/Jasmine unit tests (all specs)
  - To run a single spec file, use Karma's `--include` or temporarily scope with `fdescribe`/`fit` in the spec — there is no built-in single-file CLI filter configured in this project
- `npm run serve:ssr:nfl-predictor` — run the built Express SSR server from `dist/nfl-predictor/server/server.mjs` (see "Not actually SSR" below before relying on this)
- `ng generate component components/<name>` — scaffold a new standalone component following existing conventions

## Architecture

This is an Angular 20 app (standalone components) backed by [Neon](https://neon.com) — Postgres plus its Data API (PostgREST-compatible) and Neon Auth (managed Better Auth). The site is deployed as a fully static client-side SPA on GitHub Pages; there is no custom backend — every table access and auth call goes straight from the browser to Neon's Data API / Auth service.

The project migrated from Supabase to Neon on 2026-08-25, as a follow-up to the same migration on the sibling project `fifa-predictor` (same author, same original architecture). The schema was carried over 1:1 except one deliberate change: Supabase had a public (`anon`) `UPDATE` RLS policy on `equipos` (anyone could edit team stats without logging in) — this was dropped, so writes now always require authentication. See `schema.sql` at the repo root for the DDL (tables, RLS policies, grants) applied to the Neon project.

**Not actually SSR**, despite appearances: `@angular/ssr`, `express`, `app.routes.server.ts` (`RenderMode.Prerender` for `'**'`), and `provideClientHydration()` are all present, but there is no `main.server.ts` and `angular.json`'s build target has no `server`/`ssr`/`prerender` keys wired up. `src/main.ts` just calls plain `bootstrapApplication()`. The app builds and deploys as an ordinary client-rendered SPA (`angular-cli-ghpages`, with `404.html` = `index.html` copied for SPA routing fallback) — the SSR scaffolding is inert.

### Neon access layer

As of 2026-09-22, data access is split across several per-domain services under `src/app/services/`, the same shape as the sibling project `fifa-predictor` (used only as a loose reference — this split isn't a 1:1 copy; see the dated sections below for what's different). This replaced the original single 925-line `Service` god-class in `src/app/services/data.ts` (deleted), which had grown to cover every domain in the app.

- `src/app/services/core/supabase-client.ts` — `SupabaseClientService`, a thin injectable wrapper (`.from()`, `.auth()`, `.getClient()`) around the raw `supabase` client singleton (`src/app/core/supabase.client.ts`, unchanged — still created via `@neondatabase/neon-js`'s `createClient()` with the `SupabaseAuthAdapter`, `allowAnonymous: true`, etc.). Every domain service below injects `SupabaseClientService` instead of importing the raw client directly. `auth-guard.ts` and `login.ts` still import the raw `supabase` client directly for a couple of specific calls (unchanged from before the split).
- `src/app/services/core/etapas.ts` — dependency-free pure module (no Angular injection, no Neon calls): the `Etapa` type, `ETAPAS` labels, and the etapa-scoring formula (`registroEquipoEnEtapa`, `marcaEquipoEnEtapa`, `estadoEquipoEnEtapa`, `marcaEquipoPorEtapa`). Both `EquiposService` and `ParticipantesService` need this same win/tie/loss/points calculation, so it lives here as plain functions rather than being duplicated or forcing one service to depend on the other.
- `src/app/services/auth/auth.ts` — `AuthService`: `login`, `logout`, `getSession$`, `isAuthenticated$`, and admin user management (`createUserAsAdmin`/`listUsers`/`deleteUser`, used by `nuevo-usuario`/`borrar-usuario`). The admin calls go through Better Auth's Admin plugin via the native client — **not** `supabase.auth.admin`, which is `undefined` on the `SupabaseAuthAdapter` in `@neondatabase/neon-js@0.7.0-beta` — instead `supabaseClient.auth().getBetterAuthInstance().admin.{createUser,listUsers,removeUser}` (private `admin()` helper in `AuthService`). The admin-role check is enforced server-side by Neon Auth (verified empirically: a non-admin session gets a hard rejection from the backend, not just a hidden UI), so no extra client-side gate is needed beyond `authGuard`.
- `src/app/services/equipos.ts` — `EquiposService`: the `Equipo` interface and `getEquipos`/`getEquiposDe`/`getEquiposDeTodasEtapas`/`getEquiposConPuntajePorEtapa`. Injects `JuegosService` for the "juegos con resultado" it needs to compute per-etapa scores.
- `src/app/services/juegos.ts` — `JuegosService`: the `Juego`/`EstadoJuego` types and the whole juegos/semana domain (CRUD, week navigation, `getJuegosConResultado`, the private `enrichJuegos` logo/participant-attachment helper).
- `src/app/services/participantes.ts` — `ParticipantesService`: the `Participante`/`RegistroEquipoParticipante` interfaces, participant CRUD, `asignarNumerosAleatorios`, and `getParticipantesConPuntaje` (injects `EquiposService` + `JuegosService` for the same reason `EquiposService` does).
- `src/app/services/asignacion.ts` — `AsignacionService`: the `Asignacion` interface, `assignEquipo`, `resetAsignaciones`, `getAsignaciones`.

Each service queries the Neon tables it needs directly via `SupabaseClientService` rather than always going through a sibling service for data it could fetch itself (e.g. `JuegosService` queries `equipos`/`asignacion` directly for `enrichJuegos` instead of injecting `EquiposService`/`AsignacionService`) — cross-service injection is used only where real computed logic needs to be shared (scoring), not for raw table reads.

### RLS

`schema.sql` enables Postgres RLS on all 5 tables with the same policy shape everywhere: `SELECT` open to the `anonymous` role, full CRUD open to the `authenticated` role — no policy references `auth.uid()`/`auth.user_id()`. Neon's Data API role names are `authenticated`/`anonymous` (not Supabase's `anon`). RLS alone isn't sufficient on Neon — each role also needs an explicit `GRANT` (see the top of `schema.sql`); a policy with no matching grant is silently never evaluated.

### Domain model

The app runs an NFL season-long prediction pool with these entities (Postgres tables in Neon):

- **equipos** (`Equipo` interface) — all 32 NFL teams, grouped by `division`. Still has 7 legacy stat columns (`pg/pe/pp/pw/pd/pc/sb`) in the schema, but as of 2026-08-27 **nothing reads or writes them anymore** — they're dead weight kept only because dropping columns needs a manual migration nobody's requested. The public `equipos` page (`src/app/components/equipos/`) was updated the same day to stop displaying them: each team's row now shows a per-etapa breakdown (`EquiposService.getEquiposConPuntajePorEtapa()`) of the participant holding that team and the points it earned, one line per etapa the team is actually assigned in — same `registroEquipoEnEtapa()` calculation described below, just grouped by team instead of by participant. As of 2026-09-21 it also has `espn_id` (text, unique when non-null) mapping the row to its team ID in the ESPN API — see "Sincronización automática con ESPN" below. As of 2026-09-22 it also has `ciudad` (text), rendered before the team name on the public `equipos` page — see "Ciudad de los equipos y caché del Data API" below. It also has `ranking` (smallint, 1 = Super Bowl champion, 32 = worst regular-season team), used only to cross-check the manual assignment in the `asignacion` component against reglamento rule #2 — see "Ranking global de equipos" below.
- **participantes** — the people competing in the pool. Still has a persistent `acumulado` column in the schema, but it is **no longer read anywhere** — `ParticipantesService.getParticipantesConPuntaje()` stopped adding it to `puntaje` on 2026-08-27 (see below). Its `numero` column (used as pick/draft order, rendered as `"{{ p.numero }} - {{ p.nombre }}"` in `asignacion.html`) is no longer manually editable as of 2026-09-22 — see "Sorteo de números de participantes" below.
- **asignacion** — many-to-many assignment of teams to participants (one team per `division` per participant), scoped by an `etapa` column (`'regular' | 'wildcard' | 'divisional' | 'conferencia' | 'superbowl'`, see `Etapa`/`ETAPAS` in `core/etapas.ts`) so each playoff round has its own independent set of assignments — a team can belong to a different participant in Wild Card than in the regular season, enforced by a `UNIQUE (equipo_id, etapa)` constraint. A team's `participante` field is derived by joining `equipos` with `asignacion` in `EquiposService.getEquipos()`, not a column on `equipos` itself.
- **juegos** — schedule (`local`/`visitante` team names, `fecha`, `hora`, `semana` FK), plus `etapa` (same `Etapa`/`ETAPAS` domain as `asignacion`, added 2026-08-26) and nullable `resultado_local`/`resultado_visitante` (also added 2026-08-26, set from "Ingresar Juego"). As of 2026-08-27 these results are the **source of truth for scoring** (see below), not just informational display — `resultado_local`/`resultado_visitante` also still render on the public `Juegos de la semana` page once both are non-null (NULL/NULL means not played/entered yet, distinct from a real 0-0 score). `juegos` exists so `JuegosService.getJuegosSemanaActual()`/`getJuegosPorSemanaId()` can render "what's playing this week," and `JuegosService.actualizarJuego()` lets an admin edit any field of an existing game (recomputing `semana` from `fecha` if the date moves to another week). As of 2026-09-09 "Ingresar Juego" also has delete buttons per row (`JuegosService.eliminarJuego()`) and a "Borrar todos los juegos" action that clears the whole table (`JuegosService.eliminarTodosLosJuegos()`, an unfiltered `DELETE` expressed as `.not('id', 'is', null)` since the Data API requires a `WHERE` clause). As of 2026-09-21 it also has `espn_event_id` (text, unique when non-null), `estado` (text, default `'programado'`; one of `programado | en_vivo | final | pospuesto`), `periodo` (text, nullable — see below), and `actualizado_en` (timestamptz, default `now()`) — see "Sincronización automática con ESPN" below; these are additive columns not yet reflected in `schema.sql`'s fresh-DB DDL (same "apply manually on an existing Neon DB, then `NOTIFY pgrst, 'reload schema';`" pattern as the `etapa` column).
- **semana** — defines week date ranges (`inicio`/`fin`) for the schedule's week-by-week navigation.

### Scoring is computed from game results (2026-08-27)

There is no more manual score entry. The old "Puntajes" admin page/route and `Service.actualizarPuntaje()`/`resetPuntajes()`/`acumularPuntajesEnParticipantes()` were deleted outright (not deprecated in place) — they wrote to `equipos.pg/pe/pp/pw/pd/pc/sb` and rolled that into `participantes.acumulado`, both of which are now unused.

`ParticipantesService.getParticipantesConPuntaje()` (backs `tabla-puntajes` and the `participante-dialog` popup opened from `Home`) now computes each participant's score directly from `juegos`: it fetches every `juego` with a non-null result once (`JuegosService.getJuegosConResultado()`), plus each participant's picks across **every** etapa (`EquiposService.getEquiposDeTodasEtapas()`, already etapa-aware from the 2026-08-26 work). For each `(equipo, etapa)` pick, the pure `registroEquipoEnEtapa()` function (`core/etapas.ts`, shared with `EquiposService` — see "Neon access layer" above) scans that etapa's finished games for one where `equipo.nombre` matches `juego.local` or `juego.visitante` (matched by **name**, since `juegos` stores team names, not ids) and tallies wins/ties/losses by comparing scores. Losses count toward the visible record but contribute 0 points; a win scores that etapa's full value, a tie scores half — the same weights the old formula used (`regular`=10, `wildcard`=20, `divisional`=30, `conferencia`=40, `superbowl`=50), now applied **per etapa's own assignment** instead of always through the regular-season one. This closes the gap flagged in the 2026-08-26 asignación-por-etapa work (see below) — playoff picks now actually score.

`EquiposService.getEquiposConPuntajePorEtapa()` (backs the `equipos` page) reuses the same `registroEquipoEnEtapa()` helper from the opposite direction — per team instead of per participant — returning each team with a `porEtapa: RegistroEquipoPorEtapa[]` (etapa, label, participant, points), skipping etapas the team has no assignment in.

`Participante.equiposPorEtapa` (`{ etapa, label, equipos: RegistroEquipoParticipante[] }[]`, empty groups skipped) carries the computed `{ equipo, wins, ties, losses, puntos }` per pick straight from this calculation — `tabla-puntajes.html` and `participante-dialog.html` render it identically (both show a `wins-ties-losses` record plus `puntos` per team, grouped under an etapa heading); keep them in sync if this shape changes again, since they're two independent templates over the same data, not a shared component.

### Asignación por etapa (playoffs)

Added 2026-08-26. The `asignacion` component (`src/app/components/asignacion/`) renders one assignment grid (8 divisions × participantes, unchanged from before) per `Etapa`, switched via a `MatTabsModule` tab strip (first use of Material tabs in this codebase) — `etapaActiva` is a signal driving which etapa's rows are fetched; participantes/equipos master data loads once, only the `asignacion` rows are refetched on tab change. `AsignacionService.assignEquipo()`, `getAsignaciones()`, `resetAsignaciones()` all now take an `etapa` parameter (default `'regular'`), and the delete-before-insert in `assignEquipo()` is scoped by `etapa` too, so editing a cell in one stage cannot clear a participant's pick in another stage. "Reset" now clears only the active tab's etapa, not the whole table (behavior change from the original single-grid version).

`schema.sql` documents the resulting `asignacion` schema (fresh-DB DDL); an existing Neon database needs the `etapa` column/constraints added manually via `ALTER TABLE` (not scripted — this repo has no migration tooling), followed by `NOTIFY pgrst, 'reload schema';` (and, if that alone doesn't take effect, a compute-endpoint restart from the Neon dashboard) so the Data API picks up the new column.

### Sincronización automática con ESPN (2026-09-21)

`scripts/sync-nfl.mjs` is a standalone Node script (not part of the Angular app/build — connects to Neon directly with `pg`, not through the Data API) that pulls schedule/results from ESPN's public, unofficial, key-less endpoint (`https://site.api.espn.com/apis/site/v2/sports/football/nfl/...`) and upserts them into `equipos`/`juegos`. It has two modes, chosen with the `MODE` env var:

- **`MODE=full`** (default) — matches every `equipos` row to its ESPN team by mascot name (`team.name` in ESPN's API, e.g. "Vikings", equals `equipos.nombre`) and sets `equipos.espn_id`, then walks all 22 weeks: regular season weeks 1–18 (ESPN `seasontype=2`) and postseason (`seasontype=3`, ESPN week mapped to `etapa`/`semana` via `POSTSEASON_WEEK_MAP`: 1→wildcard/19, 2→divisional/20, 3→conferencia/21, 5→superbowl/22 — ESPN's week 4 is the Pro Bowl and is skipped). Meant to run about once a week to pick up schedule changes, postponements, and newly-defined playoff brackets.
- **`MODE=quick`** — skips the `espn_id` refresh and the full 22-week walk. It first queries our own `juegos` table (`findWeeksNearToday()`) for which `(semana, etapa)` pairs have a game with `fecha` between "yesterday" and "the day after tomorrow" in Bogotá time; if none are found it exits immediately without calling ESPN at all. If it finds one or two, it syncs only those weeks via `toEspnWeekParams()`/`ETAPA_TO_ESPN_WEEK` (the inverse of `POSTSEASON_WEEK_MAP`). Meant to run very frequently (every 5 minutes, every day) — this is what actually catches Thursday games, occasional Saturday games, early international Sunday games, and Monday Night Football, without hardcoding day/time windows and without wasting ESPN calls or CI minutes on days with nothing to sync.

For each ESPN event returned by a synced week, `upsertGame()` writes to `juegos` in this priority: update the row with a matching `espn_event_id` if one exists → else link an existing manually-entered row (no `espn_event_id` yet) matching on `semana`+`etapa`+`local`+`visitante` → else insert a new row (id = current `MAX(id)+1`, tracked in-process across the run). This means games entered by hand through "Ingresar Juego" before the first sync get adopted rather than duplicated, as long as team names/week/etapa match exactly. Dates are converted from ESPN's UTC kickoff time to Bogotá time (UTC-5, fixed offset, no DST) into the same `fecha` (`YYYY/MM/DD`) / `hora` (`HH:MM` 24h) string format the rest of the app already uses; ESPN's game status is mapped to `juegos.estado` (`programado | en_vivo | final | pospuesto`) and `actualizado_en = now()` is stamped on every write, while `resultado_local`/`resultado_visitante` stay `NULL` while `estado = 'programado'`.

**`juegos.periodo` (2026-09-22).** Free-text label of the live game phase — `'1er cuarto' | '2do cuarto' | '3er cuarto' | '4to cuarto' | 'Medio tiempo' | 'Tiempo extra'`, or `NULL` when `estado !== 'en_vivo'`. Computed by `mapPeriodo()` in `sync-nfl.mjs` from the *same* ESPN `competition.status` object `mapEstado()` already reads (`status.type.name.includes('HALFTIME')` → "Medio tiempo"; else `status.period` → quarter 1-4 via a lookup table, `>= 5` → "Tiempo extra") — no extra ESPN request and no extra GitHub Actions time, since it rides on the poll the `quick`-mode loop was already making. The frontend (`juegos.html`) renders it as-is directly under the "En vivo" badge; it does no translation/mapping of its own, so if ESPN's period numbering or halftime signaling ever changes, fix it in `mapPeriodo()`, not in the component.

Run manually with Node ≥18 (uses native `fetch`) and the `pg` dependency (already in `package.json`); on Windows, set env vars PowerShell-style:

```powershell
$env:DATABASE_URL="postgres://..."; $env:SEASON_YEAR="2026"; $env:MODE="full"; node scripts/sync-nfl.mjs
```

`DATABASE_URL` is the Neon connection string (required); `SEASON_YEAR` defaults to `2026`, `MODE` defaults to `full` if omitted.

`.github/workflows/sync-nfl.yml` runs on this repo's unlimited public-repo Actions minutes, with two `schedule` triggers: `*/5 * * * *` (every 5 minutes, every day, all day — the shortest interval GitHub cron allows) runs in `MODE=quick`; `0 6 * * 2` (Tuesday 06:00 UTC = 01:00 Bogotá, after Monday Night Football has ended) runs in `MODE=full`. A "Determinar modo" step picks `MODE` from which cron fired the run (`full` only on the `0 6 * * 2` schedule, `quick` on every other scheduled tick) or from the chosen input when triggered manually — `workflow_dispatch` exposes a `mode` dropdown (`quick`/`full`, defaulting to `quick`) for on-demand runs from the Actions tab. It reads the Neon connection string from the repo secret `DATABASE_URL` (Settings → Secrets and variables → Actions) — never hardcoded — and pins `SEASON_YEAR` to `"2026"` in the workflow itself (update it there for the next season).

**GitHub does not actually honor `*/5 * * * *` (2026-09-22).** Confirmed in production: between the workflow's first two runs, GitHub fired the schedule at 2026-09-21T21:07Z and then not again until 2026-09-22T00:06Z — a ~3 hour gap for a "every 5 minutes" cron, during which a live game (Rams @ Giants) sat showing `estado='programado'` on the public site because nothing re-synced it. This isn't a bug in this repo's YAML; GitHub's scheduler is documented to delay/skip scheduled runs under load and gives no guarantee at sub-hourly granularity, and public/low-Actions-usage repos seem to get throttled hardest.

First fix attempt (superseded, see next paragraph): made the `quick`-mode step loop internally (`while`/`sleep 240` in bash) for up to 55 minutes per job. That only helped *while a triggered job was still running* — once its 55 minutes ran out, staleness came right back if the cron didn't fire again (observed again in production: a manually-triggered run finished its loop, and the live Rams @ Giants score sat stale at "4to cuarto" for 36+ minutes with nothing re-syncing until triggered manually a second time).

**Current fix: self-chaining via the GitHub API, not cron at all.** `sync-nfl.mjs`'s `runQuick()` writes `reencadenar=true|false` to `$GITHUB_OUTPUT` (`writeGithubOutput()`, a no-op outside Actions where that env var doesn't exist) based on the exact same `findWeeksNearToday()` check that already decides whether to call ESPN — `true` when some `(semana, etapa)` has a game within the -1/+2 day window, `false` otherwise. The workflow's "Reencadenar si todavía hay un juego cerca de hoy" step reads that output (`steps.sync.outputs.reencadenar`) and, if `true`, sleeps 240s then `curl`s a `POST /repos/{repo}/actions/workflows/sync-nfl.yml/dispatches` (needs `permissions: { contents: read, actions: write }` on the job — the default `GITHUB_TOKEN` can't dispatch workflow runs without that explicit grant) to trigger a fresh `mode=quick` run of itself, passing an incrementing `intento` input as a safety counter (capped at 200 ≈ 16-17h of continuous chaining, to stop a logic bug from chaining forever — no real game window gets anywhere close to that). The chain is entirely self-sustaining once started (by cron *or* a manual `workflow_dispatch`) and needs no further cron cooperation — it keeps itself alive exactly as long as `findWeeksNearToday()` keeps finding something nearby, and stops on its own once nothing is. `concurrency: { group: sync-nfl, cancel-in-progress: false }` still queues rather than overlaps if the flaky cron does happen to fire while a chain is active. `timeout-minutes: 10` on the job is enough for checkout+install+sync+the 4-minute sleep+dispatch; it does **not** need the old 60+ minute budget since the job no longer stays alive for the whole polling window itself. If you touch this workflow, keep both halves in sync: `reencadenar`'s logic in the script and the dispatch step's use of it.

**"En vivo" en `Juegos de la semana` (2026-09-21).** `JuegosService.getJuegosPorSemanaId()`/`getJuegosSemanaActual()` already select `juegos.*`, so `estado` flows through without any service change; it was added to the `Juego` interface as `estado?: EstadoJuego` (`EstadoJuego = 'programado' | 'en_vivo' | 'final' | 'pospuesto'`, `src/app/services/juegos.ts`). The `juegos` component (`src/app/components/juegos/`) uses it in two ways:

- **Display priority**: `juegos.html`'s per-game "scheduled" cell used to show "Final" whenever `resultado_local`/`resultado_visitante` were non-null. That broke once the ESPN sync started writing partial scores while a game is still in progress (`estado='en_vivo'`, resultado already set) — a live game would render as "Final". The cell now branches on `estado === 'en_vivo'` first: if true, it shows *only* the pulsing "En vivo" badge plus `j.periodo` underneath when present (no `hora`/clock icon — deliberately dropped so nothing implies a kickoff time for a game already in progress); otherwise it falls back to the original `resultado_local !== null && resultado_visitante !== null` check → "Final", else the scheduled `hora`. This keeps old manually-entered finals (no `estado`, defaulted to `'programado'` by the schema) working unchanged.
- **Auto-refresh**: `Juegos` (`juegos.ts`) polls `JuegosService.getJuegosPorSemanaId()` every 60s (`REFRESH_INTERVAL_MS`) via `setTimeout`, but only while `hayJuegosEnVivo()` is true for the currently displayed week — `scheduleAutoRefresh()`/`refreshGamesQuietly()` re-arm each other after every fetch and stop rearming once no game in the week is `en_vivo`, so weeks with nothing live never poll. The refresh is "quiet": it skips the `loading` flag/spinner (`refreshGamesQuietly()` is a separate path from the initial `loadGames()`), just replacing `juegosAgrupados` and calling `cdr.detectChanges()` (the component is `OnPush`). The pending timeout is cleared on week navigation (`prevWeek()`/`nextWeek()`) and `ngOnDestroy()` so a stale refresh can't land on the wrong week or a destroyed component. Since the GitHub Action's `quick` sync only runs every 5 minutes, this client-side polling surfaces a new score within at most ~1 extra minute of whenever the next sync lands, not in real time.

### Sorteo de números de participantes (2026-09-22)

The manual "Número" input on the `participantes` component (both the create form and the inline edit row) was removed — `participante.numero` is no longer something an admin types in directly. It's now assigned in one shot for every participant via a "Sortear números" button (`Participantes.sortearNumeros()`, `src/app/components/participantes/participantes.ts`, behind a `confirm()` since it overwrites whatever numbers were there), which calls `ParticipantesService.asignarNumerosAleatorios()` (`src/app/services/participantes.ts`): it fetches all participants, generates a Fisher–Yates shuffle of `1..N` (N = participant count), and updates every row's `numero` in one `forkJoin` of per-row `UPDATE`s. `ParticipantesService.createParticipante(nombre)` no longer takes a `numero` argument either — since the column is `NOT NULL` with no DB default, it auto-assigns `MAX(numero) + 1` as a throwaway placeholder on insert (a `SELECT` before the `INSERT`); that placeholder is only there to satisfy the constraint and is expected to be overwritten the next time someone clicks "Sortear números", not a real draft-order assignment. There's no uniqueness constraint on `numero` in the schema, so nothing stops two participants from temporarily sharing a placeholder before the next draw.

### Ciudad de los equipos y caché del Data API (2026-09-22)

`equipos` gained a `ciudad` column (text, e.g. `"Buffalo"` for the Bills) — added directly in Neon and populated for all 32 teams, not yet reflected in `schema.sql`'s fresh-DB DDL (same "additive column, apply manually" situation as `espn_id`/`logo_2` before it). `Equipo.ciudad` was added to the interface (`src/app/services/equipos.ts`), and `equipos.html` now renders `{{ e.ciudad }} {{ e.nombre }}` (e.g. "Buffalo Bills") instead of just the team name.

**Gotcha:** right after adding the column, Neon's Data API kept omitting `ciudad` from `select=*` queries against `equipos`, even though `describe_table_schema` confirmed the column existed with data for every row, and even though selecting it explicitly (`select=nombre,ciudad`) returned it correctly — a schema cache staleness scoped specifically to wildcard expansion. Neither `NOTIFY pgrst, 'reload schema';` nor a full compute-endpoint restart (`restart_postgres_endpoint`, tried after the NOTIFY alone didn't work) fixed it, unlike the documented NOTIFY-then-restart sequence that worked for the `etapa`/`espn_event_id` columns before. The actual fix was to stop relying on `select('*')` for this query: `EquiposService.getEquiposConPuntajePorEtapa()` (backs the `equipos` page) now selects an explicit column list (`id,nombre,ciudad,division,logo,pg,pe,pp,pw,pd,pc,sb`) instead of `'*'`. If a future column addition shows the same symptom (present via `describe_table_schema`/explicit-select, missing from `select=*`), reach for an explicit column list in the affected query rather than assuming another NOTIFY/restart cycle will eventually catch up.

### Ranking global de equipos (2026-09-22)

Reglamento rule #2 assigns teams to participants following "el ranking global de la temporada anterior" (`equipos.ranking`, smallint: 1 = Super Bowl champion, 32 = the team with the worst regular-season record — the inverse of NFL Draft order). This exists purely so an admin can cross-check that the manual assignment made in the `asignacion` component actually followed that rule; nothing in the app UI reads or displays `ranking` yet.

**Why not just load ESPN's actual Draft order:** ESPN's core API does expose the completed Draft pick-by-pick (`sports.core.api.espn.com/v2/sports/football/leagues/nfl/seasons/{year}/draft/rounds`), and its team references match `equipos.espn_id` directly — but round 1 reflects the *actual, post-trade* picks: verified live for the 2026 draft, only 24 of 32 teams appear in round 1 (some picked 2-3 times after trading up, 8 teams have zero picks because they traded their slot away). That data can't be turned into a clean 1-32 ranking per team. It's also not available ahead of time: `seasons/{year}/draft` for the season still being played returns `"picks": []` until ESPN populates the actual draft (~April) — confirmed live for the 2027 draft while the 2026 season was in progress, so relying on it wouldn't let this run automatically right when the Super Bowl ends anyway.

**What we do instead:** `scripts/sync-ranking.mjs` computes the ranking itself from ESPN's plain scoreboard results (`site.api.espn.com/.../scoreboard?dates={year}&seasontype={2|3}&week={n}` — historical seasons work with `dates`, not `year`, which silently returns the *current* season instead) using the NFL's own published draft-order rule, inverted:

1. The 18 non-playoff teams, worst-to-best regular-season record.
2. The 6 Wild Card losers, worst-to-best regular-season record.
3. The 4 Divisional Round losers, worst-to-best.
4. The 2 Conference Championship losers, worst-to-best.
5. The Super Bowl loser.
6. The Super Bowl winner.

Each team's furthest playoff round is found by walking `wildcard → divisional → conferencia → superbowl` in order and always overwriting a per-team map, so the last write is necessarily their furthest appearance. Ties within a group on win% are broken by strength of schedule (average opponent win%, weaker schedule sorts as "worse" — the same direction the NFL uses for actual draft-order tiebreaks), computed from the same regular-season game log already fetched, no extra requests. The resulting worst-to-best order (draft position 1-32) is inverted (`ranking = 33 - posición`) and written with a single `UPDATE ... FROM (VALUES ...)` matched by team name.

**Timing:** SEASON_YEAR here means the same thing it means in `sync-nfl.mjs` — the season being ranked, not the calendar year of the draft it feeds (e.g. `SEASON_YEAR=2025` was used for the one-off initial load, to rank the 2025-2026 season that produced the actual April-2026 draft). Since the computation only depends on our own historical scoreboard data — available the moment the Super Bowl ends — `.github/workflows/sync-ranking.yml` runs it daily from Feb 1-20 (`0 12 1-20 2 *`, comfortably bracketing the Super Bowl's usual date) plus `workflow_dispatch` for manual runs; the script itself checks this database's own `juegos` row with `etapa='superbowl'` first and exits without calling ESPN at all if that game has no result yet, so the early daily runs in the window cost nothing. `SEASON_YEAR` is pinned in the workflow (same pattern as `sync-nfl.yml`) and needs updating there each year.

The initial load (2026 draft / 2025-2026 season) was run once by hand via direct SQL against Neon rather than through the script with a materialized `DATABASE_URL`, since Claude Code's auto-mode classifier blocks putting a raw DB credential into a shell command; the ranking math was run client-side in a browser tab against the same ESPN endpoints instead, and the result written with `UPDATE equipos ... FROM (VALUES ...)`. A human running `scripts/sync-ranking.mjs` locally or in CI (where the secret comes from `secrets.DATABASE_URL`, not a typed command) doesn't hit this restriction.

### Auto-asignación de temporada regular por ranking (2026-09-22)

`AsignacionService.autoAsignarTemporadaRegular()` implements reglamento rules #2, #5, #7 and #8 to fully automate the "Temporada Regular" grid, exposed as an "Auto-asignar" button on the `asignacion` component's Temporada Regular tab only (hidden on the playoff tabs — the ranking-based algorithm only applies to the regular-season assignment; playoff-round assignment follows a different, puntaje-based rule (#9+) that isn't automated). It reads `participantes`/`equipos` fresh on every call — deliberately not assuming any ordering between when `equipos.ranking` gets loaded (see above, right after the Super Bowl) and when the next season's participants/`numero` draw exist, since those two things can happen in either order.

**Algorithm** (built and verified incrementally across several conversation turns, comparing each round's output against a manually-built assignment before trusting the next one): equipos are walked once in ranking order (1 = best) and hard the whole way through, distributed across the participants in fixed-size "rounds" of `N` (`N` = participant count) — round 1 in ascending `numero` order, round 2 descending, alternating every round (rule #5), for as many complete rounds as `Math.floor(equipos.length / N)` allows (currently 4, with 8 participants and 32 teams; genuinely N-agnostic — with e.g. 7 participants it does 4 rounds of 7 = 28 teams, leaving the 4 worst-ranked teams unassigned rather than giving one participant an uneven 5th team). Within a round, each team is offered to the front of that round's participant queue; a participant is skipped (team offered to the next-in-queue instead, immediately, exactly per the reglamento's wording) when they already hold another team from that division (#7) or already hold two teams from that team's conference (#8, "tercer equipo de una conferencia") — the skipped participant is *not* removed from the queue, so they're first in line again for the very next team, which is what rule #7's "el siguiente equipo le será asignado al participante que fue saltado" describes. `autoAsignarTemporadaRegular()` fully replaces `asignacion` for `etapa='regular'` (delete-then-insert) rather than patching individual cells.

One discrepancy surfaced during verification: a hand-built assignment had `Titans`↔`Tomás` and `Raiders`↔`Juan R` swapped relative to the algorithm's `Titans`↔`Juan R`/`Raiders`↔`Tomás`. Traced by hand pick-by-pick and confirmed the algorithm is correct — at that point in the queue (descending `numero`: ..., Juan R(4), ..., Tomás(2), ...) Juan R was skipped once earlier in the round and, per rule #7, got first crack at the very next team (Titans) before the queue ever reached Tomás; the manual assignment hadn't re-offered the skipped participant the next pick immediately. Confirmed as a one-off manual error, not an algorithm bug — worth remembering if a future manual-vs-algorithm mismatch shows up again, since "who was skipped most recently gets served first" is easy to get wrong by hand but is exactly what the code enforces.

### `left_mascot`/`right_mascot` reemplazan `logo`/`logo_2` (2026-09-22)

`equipos.logo`/`equipos.logo_2` (each team's two mascot-art images, used to put a mirrored pair of illustrations on either side of a card/row) were renamed at the data level to `left_mascot`/`right_mascot` — additive columns, copied from the old ones (`left_mascot = logo`, `right_mascot = logo_2`) rather than an in-place `ALTER TABLE ... RENAME COLUMN`, so the cutover could be verified with both old and new columns live before dropping anything. Every read site was repointed in the same pass: `Equipo.logo` → `Equipo.left_mascot` (`src/app/services/equipos.ts`, all four query methods and their explicit `select()` column lists), and `JuegosService`'s `enrichJuegos()`/its two `equipos` queries (`v?.logo` → `v?.left_mascot`, `l?.logo_2 || l?.logo` → `l?.right_mascot || l?.left_mascot`) — the `Juego.logoVisitante`/`logoLocal` field names themselves were left alone since they aren't the renamed columns, just derived fields populated from them. Templates updated: `equipos.html`, `participante-dialog.html`, `tabla-puntajes.html` (`e.logo`/`item.equipo.logo` → `...left_mascot`); `juegos.html` needed no change since it already reads the unrenamed `j.logoVisitante`/`j.logoLocal`. `logo_2` was dropped after verifying; `logo` was **not** dropped (only asked to remove `logo_2`) — it's now dead/unused, same as the legacy `pg/pe/pp/pw/pd/pc/sb` stat columns noted above, kept only because nobody's asked for the cleanup.

Two of the three `equipos.select('*')` wildcard queries that existed before this change (`JuegosService.getJuegosSemanaActual()`/`getJuegosPorSemanaId()`) were switched to explicit column lists (`id,nombre,left_mascot,right_mascot`) as part of this same edit, both to keep the query minimal and to sidestep the wildcard-select schema-cache staleness documented above for `ciudad` — untested whether `left_mascot`/`right_mascot` would have hit the same gotcha via `select('*')`, deliberately not finding out. `EquiposService.getEquipos()` was converted the same way. If a future `equipos` query still uses `select('*')` and a newly-added column doesn't show up in it, this is the second time that exact fix has worked — reach for it before another NOTIFY/restart cycle.

**Verifying image loads in this environment:** `equipos.html`'s `<img loading="lazy">` never actually loads in Claude's sandboxed preview browser (`img.complete` stays `false` indefinitely; forcing `img.loading = 'eager'` on the same element loads it instantly) — confirmed unrelated to this rename (pre-existing attribute, untouched) and most likely a headless/automation quirk with native lazy-loading's viewport/IntersectionObserver detection rather than a real bug; `tabla-puntajes.html`/`participante-dialog.html` (no `loading="lazy"`) rendered the same renamed field correctly in the same session. Don't diagnose a blank `equipos` page logo as a data/rename bug without first checking whether it's just this.

### Routing & auth

Routes are defined in `src/app/app.routes.ts`. Admin/management routes (`admin`, `nuevo-usuario`, `borrar-usuario`, `ingresar-juego`, `participantes`, `asignacion`) are protected by `authGuard`; `login` is protected by `guestGuard` (redirects to `/admin` if already authenticated). Public routes (`''`, `tabla-puntajes`, `equipos`, `juegos`, `reglamento`) require no auth. Unlike `fifa-predictor`, user creation/deletion are two separate routes (`nuevo-usuario`, `borrar-usuario`) rather than one combined `usuarios` page, and there is no FIFA-Annex-C-style manual bracket-seeding step (no knockout bracket in this domain).

### Component conventions

Components are standalone and import Angular Material modules directly per-component (no shared Material module). Most data-loading components use RxJS (`forkJoin`/`switchMap`) directly against the domain services' methods rather than `async` pipes throughout.
